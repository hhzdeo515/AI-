# 端侧适配设计（AI 智能眼镜）

> 状态：**设计定稿，待评审** ｜ 版本 v1 ｜ 对应代码 `assistant-lite/`（P0–P12 已完成）
> 本文只回答一个问题：**眼镜端只有 1–3B 模型，现有的 `assistant-lite` 要怎么改才能接上去。**

---

## 0. 一句话结论

现有 `Task → orchestrator → agent → Reply` 这套编排是对的资产，**不需要推翻**；要改的是它的**入口契约**——从「用户提交文字 + 文件」改成「端侧模型判定后的传感器事件包」。

端侧 1–3B 只做三件事：**唤醒 / 意图识别 / 决定是否上行**。云端保留全部权威判定权。

---

## 1. 前提（已确认，不再讨论）

| 编号 | 前提 | 影响 |
|---|---|---|
| C1 | 端侧模型 1–3B，**只做判断决策、意图识别，并兼唤醒** | 端侧不做 VLM / 不做长文生成 / 不做解题 |
| C2 | 输入只有三类：**麦克风、IMU、摄像头** | 无 PPG，故**无心率**（见 §5 边界 5） |
| C3 | **IMU 本版不做**，但**保留通道** | MVP 不实现，契约里预留，不给假数据 |
| C4 | 断连期间本地缓存，重连后补传（对标消费级 AR 眼镜的实机体验） | 上行必须是**幂等 + 可重放**的 |
| C5 | 全部重活走云端（百炼 qwen-plus / qwen-vl-max / cosyvoice-v1） | 现有 `llm.py` 不动 |

### C3 的执行纪律

契约里给 IMU 预留一个 `kind="imu"` 位，但 **MVP 阶段任何地方都不得写入、不得伪造、不得在 UI/PRD 里宣称有 IMU 能力**。

理由：本项目已经踩过一次同类坑——`exam` agent 曾经只塞了个假的 `artifact` 而没写 `_archive`，导致**题解静默地从不落库**，跑真实链路才发现。**"看起来接了、其实没接"比"明确没接"危险得多。**

## 2. 端 / 云职责切分

```
┌─ 端侧（1–3B + 规则） ────────────────────────┐
│ ① 唤醒        KWS / 1-3B → 是否在跟我说话    │
│ ② 意图识别     → intent 枚举 + confidence     │
│ ③ 上行决策     → 丢弃 / 追认 / 上行（四态）   │
│ ④ 本地队列     落盘、重连补传、超时保底         │
└───────────────────┬──────────────────────────┘
                    │ 事件包（intent + 音频/图片 + 时序 + request_id）
┌───────────────────▼──────────────────────────┐
│ 云端 assistant-lite（现有代码）               │
│ ⑤ 权威路由   orchestrator.route() 五级        │
│ ⑥ 场景执行   meeting / exam / fitness / ...   │
│ ⑦ 播报语生成  speech + tts + 代际号            │
│ ⑧ 归档        session.archive()               │
└──────────────────────────────────────────────┘
```

### 关键设计决策：端侧判定**不具备权威性**，云端必须复核

端侧 1–3B 把"这道题怎么解"误判成 `general`，云端就会被喂错 Agent，用户拿到答非所问的结果，而**端侧永远不会知道自己错了**——故障静默级联。

而云端复核的成本几乎为零：`orchestrator.py:103-145` 的前三级（事件映射 / 显式指定 / 关键词）是纯规则零 token，第四级粘性是纯状态判断。

所以：
- 端侧 `intent` 进入云端后，**降级为提示**，与现有 `scene_hint` 同优先级（`orchestrator.py:114`）
- 云端 `ACTION_MAP`（`orchestrator.py:28`）保持**权威**
- 端侧判错率**必须可统计**，否则无法迭代（见 §8 指标）

## 3. 端侧契约

### 3.1 定型意图枚举（`intent`）

端侧 1–3B **只允许输出这 11 个值之一 + 置信度**。不允许自由文本。

| `intent` | 语义 | 云端映射 | 上行时机 |
|---|---|---|---|
| `wake` | 被唤醒，无具体请求 | 不上行 | — |
| `stop` | 停止播报 / 别说了 / 停 | `stop_playback` → `general` | 立即 |
| `switch_scene` | 切到会议 / 解题 / 锻炼 / 资料 | `switch_scene` + `event.scene` | 立即 |
| `meeting_start` | 开始会议 / 开始记录 | `start_meeting` → `meeting` | 立即 |
| `meeting_append` | 会议进行中的话 | `append_meeting` → `meeting` | **流式/延迟** |
| `meeting_summarize` | 生成纪要 / 总结会议 | `summarize_meeting` → `meeting` | 同步 |
| `meeting_stop` | 结束会议 | `stop_meeting` → `meeting` | 立即 |
| `solve` | 拍题 / 解这道题 / 看看这个 | `solve_captured_question` → `exam` | **异步** |
| `train_start` | 开始训练 + 动作名 | `start_exercise` → `fitness` | 立即 |
| `train_done` | 做完一组 / 下一组 | `set_done` → `fitness` | 立即 |
| `train_pain` | 某部位疼 / 不舒服 | `pain_report` → `fitness` | **立即、最高优先** |
| `cancel` | 算了 / 取消 / 不用了 | 不上行（本地清队列） | — |

> 与现有 `ACTION_MAP` 的关系：新增的只有一个 `switch_scene` 的 device 触发路径，其余全部已有映射，**云端 `ACTION_MAP` 无需改动**。

**为什么定成固定枚举而不是自由文本**：自由文本 intent 需要云端再加一层归一化，那层归一化一旦判错，端侧的判错率就**无法归因**——分不清是端侧判错还是归一化判错。固定枚举让"端侧判对率"变成一个可以直接跑评测集的数字。

### 3.2 置信度与四态判定

端侧**不是二值决策**，而是四态：

```
confidence ≥ 0.75           → UPLOAD      上行
0.45 ≤ confidence < 0.75    → CONFIRM     本地短问一句「你是要…吗？」
confidence < 0.45 且非唤醒后 → DROP        丢弃，不上行（省电省流量）
唤醒后仍 < 0.45             → FALLBACK    上行原始音频，交云端判
```

- **`DROP` 是主要的省电机制**，也是最容易被做错的地方：环境噪声、旁人对话、电视声音都该在这里被拦掉。
- **`FALLBACK` 是安全网**，保证"端侧不会因为模型弱而彻底不能用"。
- `train_pain` **跳过四态判定，永远 `UPLOAD`**。安全相关不可降级——这与现有 `fitness/state.py:355` 的不适即停设计一致。

阈值 0.75 / 0.45 是**待校准的初值**，必须用真机数据回归（见 §8）。

### 3.3 ⚠️ 唤醒功耗：一个需要真机决策的风险

**1–3B 常驻做唤醒（KWS），误唤醒率与待机功耗通常比专用 KWS 小模型差一个量级。** 眼镜是戴在脸上的电池设备，这条会直接影响可用续航。

三种形态对比（**需真机实测后拍板**）：

| 方案 | 待机功耗 | 误唤醒 | 端侧模型数 | 备注 |
|---|---|---|---|---|
| 专用 KWS 小模型 + 1–3B 做意图 | 最低 | 最低 | 2 个 | 需两套模型与调度 |
| **1–3B 兼唤醒（当前前提 C1）** | 高 | 较高 | 1 个 | 实现最简，但需实测续航 |
| 按键/手势唤醒 + 1–3B 做意图 | 几乎为零 | 无 | 1 个 | 失去"免手"卖点，与眼镜定位冲突 |

**本设计按 C1（1–3B 兼唤醒）编写**，但 §8 指标里必须包含**待机功耗与误唤醒率**两项；若实测续航不达标，回退到方案一**不需要改云端任何代码**（端侧契约不变）。

## 4. 设备 → 云端协议

### 4.1 不新增接口，复用 `/api/chat`

现有 `/api/chat` 已支持 `text / scene / event / files / owner / session_id / request_id` 七个字段（`web/app.py:78-112`），其中 `event` 已是任意 JSON 对象（`web/app.py:94-101`）。

**决策：device 字段走 `event` 内部，不扩 `_parse_chat_form`。**

理由：
1. `event` 本来就是"结构化事件入口"的定位，device 元数据属于它
2. 现有 `/api/chat` 与 `/api/chat/async` 共用 `_parse_chat_form` + `_run_chat`（`web/app.py:78`），扩接口要动两处，**极易漂移**——`event` 字段被丢弃过一次（P9.1 修的），就是这类漂移
3. 端侧只有一个上行通道，协议越窄越不容易出错

### 4.2 完整事件包

设备把 1–3B 的输出映射成 `event`：

```json
{
  "semantic_action": "set_done",
  "device": {
    "id": "glasses-8f3a2c",
    "intent": "train_done",
    "confidence": 0.91,
    "model": "qwen2.5-1.5b-instruct",
    "rssi": -62
  },
  "t_capture": "2026-09-22T18:03:11.482+08:00",
  "t_speech_end": "2026-09-22T18:03:11.150+08:00",
  "trace_id": "8f3a2c-000117"
}
```

提交形式（与前端 `form()` 完全一致，`app.js:177-186`）：

```
POST /api/chat   (multipart/form-data)
  owner          = glasses-8f3a2c       # 设备即 owner，沿用现有 owner 隔离
  session_id     = sess-20260922-1
  request_id     = 8f3a2c-000117        # 设备生成，本地队列持久化，重放不变 ★
  text           = ""                    # 端侧没做 ASR 时留空，云端从音频转写
  event          = {上面的 JSON}
  files          = [chunk.wav]           # 可选：唤醒后的一段音频
```

**★ `request_id` 是整个断连补传机制的地基**，见 §5。

### 4.3 云端需要的改动（很小）

| 改动 | 位置 | 说明 |
|---|---|---|
| 未知 `intent` 不硬失败 | `orchestrator.py:104` | `event.device.intent` 缺席或未知时，**静默忽略**，不能影响 `semantic_action` 的既有路由 |
| device 意图来源打标 | `orchestrator.py:191`（`handle` 调 `route` 处） | 路由来源新增 `"device"`，与现有 `event / hint / keyword / sticky / llm` 并列（`orchestrator.py:100`），**用于统计端侧判对率** |
| `switch_scene` 支持 device 字段 | `orchestrator.py:109` | 场景值从 `event.get("scene")` 读，已有，无需改 |
| 时序字段落库 | `session.py` 新增列 | `t_capture` / `t_speech_end` / `device_id` / `intent` / `confidence`，用于时延拆段与判对率统计 |

**不需要改**：`ACTION_MAP` 全部映射、五级路由顺序、`Task`/`Reply` 双契约、`tools/`、各场景 Agent。

### 4.4 新增两个小接口

```
GET /api/payload?request_id=<id>
    → {"known": true|false, "status": "...", "scene": "...", "action": "..."}

GET /api/speech/latest?owner=&session_id=&since=<gen>
    → {"generation": 3, "has_new": true, "speech": "答案是B。"}   # 无新内容时 speech 为空
```

**`/api/payload` 解决什么**：设备发完请求、连接断了、**没收到响应**。此时云端可能已经处理并归档了。重连后设备先 `GET /api/payload` 查一次（`session.receipt()` 已存在于 `session.py:128`），命中就不重发——否则会产生**孤儿归档**（题解存了两份）。

**`/api/speech/latest` 解决什么**：见 §6 竞态。

## 5. 断连与补传

### 5.1 现有资产：去重已经做对了

`Orchestrator.handle` 第一件事就是查 `receipt(task.owner, task.request_id, "handle")`，命中直接返回 `STATUS_DUPLICATE`（`orchestrator.py:184-187`），底层是 `receipts(owner, request_id, stage)` 主键表（`session.py:28-34`）。

**结论：只要设备保证"同一份 payload 重放时 `request_id` 不变"，云端天然幂等——不会重复归档、不会重复播报、不会串题。** 这正是实机里"拍完录完、连上了再上传"所需的服务端一半。

> 反过来讲：`request_id` 如果设备每次重试都重新生成，这套机制**完全失效**，而且失效得很安静。设备端必须把 `request_id` 在生成 payload 时就写进本地队列，而不是发送时生成。

### 5.2 设备端本地状态机

```
RECORDED ──发送──▶ INFLIGHT ──收到 2xx──▶ ACKED ──可删本地──▶ (cleanup)
   ▲                   │
   │                   └─超时/断连─┐
   └───────────────────────────────┘  重连后：
                                        ① GET /api/payload?request_id
                                        ② known=true  → 直接 ACKED
                                        ③ known=false → 重发（request_id 不变）
```

- **本地容量上限**：建议「时长 + 体积」双限（如录音 30 分钟 / 媒体 200 MB），超限按「先证据后闲聊」淘汰——`train_pain`、`solve` 的图片**永不淘汰**。
- **重连不弹窗、自动补传**，与消费级 AR 眼镜体验一致；用户可事后在手机端看到结果并选择是否留存。
- **本轮 MVP 不含**：多设备并发、跨设备合并会话、云端主动拉取（poll）。

### 5.3 明确不做（本版）

- ❌ 服务端维护 `pending_payloads` 登记表预测设备将发什么——服务端**不可能知道**"设备断连前录了什么"，那是设备本地状态。**只有设备能回答。**
- ❌ 服务端主动拉取设备队列（需要设备常驻可连，与省电冲突）。

## 6. 播报打断：一个必须补的竞态窗口

现有机制（正确的一半）：`stop_playback` 事件让服务端播报代际号 +1（`general.py:34-43`），`/api/speak` 与 `/api/playback` 带代际号（`web/app.py:201-242`）。

**但有一个窗口**：用户说"停" → 云端代际号 +1 → 设备丢弃当前音频 ✅。可是如果**云端不返回新内容**，设备不知道该播什么，旧文本对应的 `/api/speak` 也不会自动重取 —— 表现为「静默了，但没有新播报」，用户不知道系统听没听见。

**设计：代际号权威在设备侧，不在服务端。**

```
设备收到 stop（本地判定，不等云端）：
    1. local_gen += 1
    2. 立即停播，丢弃 local_gen 之前的所有音频  ← 不等云端确认
    3. 用同一个 request_id 上行 stop 事件（云端代际号 +1 仅用于一致性/调试）
    4. 若 3 秒内没有新内容：播一句「已停止」的本地提示音（TTS 缓存，不联网）
```

要点：
- **打断必须由端侧立即完成**，不能等云端往返——这与代码里"设备端只需实现比对与停播"的定位一致
- **"没收到新内容"必须有明确反馈**，否则用户面对的是无反馈的静默
- 端侧需要一小段**离线提示音缓存**（"已停止"/"没听清"/"网络不可用"），否则断连时设备完全哑巴

## 7. 五条边界与处置

| # | 边界 | 风险 | 处置 | 谁决策 |
|---|---|---|---|---|
| 1 | 端侧意图判错 | 静默级联到错 Agent | 云端权威复核 + `source="device"` 打标统计判对率 | 工程 |
| 2 | 1–3B 兼唤醒功耗 | 续航不达标 | 三种形态实测对比（§3.3），回退不改云端 | **产品 + 硬件** |
| 3 | 打断竞态 | 静默无反馈 | 代际号权威移到端侧 + 3s 保底提示（§6） | 工程 |
| 4 | 录音分片边界 | 会议转写丢字 | 设备侧按静音端点切分，**段间保留 500ms 重叠**；`tools/audio.py` 的 240s 切片用于超长上传，两者并存不冲突 | 工程 |
| 5 | 无 PPG → 无心率 | PRD/宣发过度承诺 | `fitness` 是 **IMU + 主观感受** 驱动；**禁止**出现"心率区间/实时心率"表述 | **产品（PRD 必须改）** |

### 边界 5 展开

已确认输入只有麦克风 / IMU / 摄像头，**没有 PPG**。因此现有 `fitness` 场景里所有依赖生理数据的能力都不存在：无法算心率区间、无法算训练负荷、无法做恢复度评估。

可以做的（IMU 能支撑）：动作类型识别、次数/组数、节奏与组间恢复时长、左右不平衡、异常停顿。
不能做的：心率、血氧、卡路里（只能给粗估且需标注误差）。

**当前 PRD 与简历材料里若出现心率相关内容，需一并清理。**

## 8. 指标（MVP 必须能测）

端侧加入后，"路由准确率"这个指标被拆成两段，必须分开测，否则无法归因：

| 指标 | 定义 | 目标 | 测法 |
|---|---|---|---|
| **端侧判对率** | 端侧 `intent` 与云端权威路由一致的比例 | ≥ 90% | 测完 `source="device"` 后云端是否发生 reroute |
| **端侧拒识率** | 噪声/旁人对话被正确 `DROP` 的比例 | ≥ 95% | 离线评测集 |
| **误唤醒率** | 每小时非唤醒触发次数 | ≤ 0.5 次/h | **真机实测** |
| **待机功耗** | 唤醒常驻状态下的电流 | 待定 | **真机实测** |
| **补传成功率** | 断连 payload 重连后成功送达比例 | ≥ 99.5% | 设备埋点 |
| **端到端时延拆段** | 端侧判定 / 上行 / 云端处理 / TTS / 下行 各段 | — | 靠 `t_capture` / `t_speech_end` 落库 |

> `端侧判对率` 这一项**只有固定枚举契约才能测**（§3.1），这是把意图定成枚举的第二个理由。

## 9. MVP 范围（本版做什么）

### 做

| # | 内容 | 交付物 |
|---|---|---|
| 1 | 本文档 | `docs/端侧适配设计_眼镜.md` |
| 2 | `event.device` 契约落地：`intent` / `confidence` / `device_id` | `orchestrator.py` 路由来源打标 + 时序/判对率落库 |
| 3 | 未知 intent 静默忽略（不污染既有路由） | 回归测试补一条 |
| 4 | `GET /api/payload?request_id=` 幂等查询 | `web/app.py` + 测试 |
| 5 | `GET /api/speech/latest` | `web/app.py` + 测试 |
| 6 | **设备模拟器**（核心交付） | 命令行脚本，模拟 1–3B 输出 + 断连重放 |
| 7 | 端侧意图评测集 | `tests/test_device_contract.py` + 意图用例表 |

### 第 6 项为什么是核心交付

**没有真机也能验证整条端云链路。** 模拟器按 §3.1 枚举生成 `event`，随机注入断连、重复发送、乱序、超时，用来验证：幂等是否真的生效、未知 intent 是否真的不影响路由、断连补传是否会产生孤儿归档。

这与项目既有的测试纪律一致——**160 项测试不依赖任何外部 API**，端侧这条链路同样应该能在没有眼镜的情况下回归。
