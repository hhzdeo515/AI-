# 拍照解题指标体系与埋点方案

更新日期：2026年9月30日。

**北极星：限时作答净增量 Δ** —— 相同限时、相当题目下，用产品的人均「确认采用」作答数，减去用原方式的人均采用数：

> Δ = C产品/M产品 − C原方式/M原方式

采用由用户或测试观察当场明确记录，不以模型正确率、生成答案或复制粘贴代替。要算 Δ 只需要三个数：**多少人测了（M）、做了多少题（Q）、采用了多少题（C）**。下面九个事件就是为了把这三个数记准，并解释没采用的题卡在哪。Δ 能否提前预示复用/留存，仍待真实数据验证。

## 九个事件：埋在哪里、为什么埋在这里

| 事件 | 埋在哪里 | 为什么埋在这里 |
|---|---|---|
| `test_session_started` | 测试计时页，用户点「开始测试」的一刻（终端） | 计时窗口和人数 M 只能由测试现场定义；预算必须从用户真正开始那一刻起算，由服务端代记会引入时钟争议 |
| `test_session_ended` | 计时到点或用户中途退出的一刻（终端） | 截止时每道题的最终状态只有终端看得全；中途退出的人靠这个事件留在分母里，退出的人不能凭空消失 |
| `exam_attempt_started` | 用户对某道题开始作答时（终端或测试观察记录） | Q 数的是「开始做的题」：补拍、重试、失败都还算同一道题，所以在开始时记一次，后续事件都挂在它下面 |
| `exam_input_finished` | 拍照/上传完成时（手机端输入入口） | 拍糊、补拍、资料拍不全，这些阻力只有输入端看得见；服务端只能拿到最后一张图，看不到过程 |
| `exam_task_finished` | 云端处理结束时（服务端） | 处理耗时、失败、重试、调用成本只有服务端知道——九个事件里唯一必须埋在服务端的一个 |
| `exam_result_presented` | 结果真正显示到屏幕上时（终端渲染完成） | 「算完了」不等于「用户看到了」。采用只能引用用户亲眼见过的结果，所以展示回执必须由展示端出 |
| `exam_answer_recorded` | 用户写下或确认最终作答时（答题记录处） | 证明「形成了作答」；同时记下作答版本，之后一旦改答，就知道旧确认要作废 |
| `exam_adoption_changed` | 用户点「采用/不采用/犹豫/撤回」时（终端） | 北极星的 C 直接来自这里。采用必须绑定当前作答版本：改了答案要重新确认，撤回不算采用 |
| `exam_action_recorded` | 追问、查证、放弃等行为发生时（终端或观察） | 回答「为什么没采用」：卡在阅读、查证还是决策，决定下一版改哪里 |

每条事件只带四个必带信息：**谁（user）、哪次测试（session）、哪道题（question）、开始测试后第几毫秒**。其他字段服务端能补的，不让终端背。

## 三个数的口径

- **M（人数）**：点了「开始测试」的人都算，包括一道题没做和中途退出的。
- **Q（题数）**：开始作答的题去重计数；失败、超时、放弃的题也算在内。
- **C（采用数）**：截止时状态为「采用」的题；改过答案必须重新点一次采用，撤回的不算。
- 记录缺失一律标「待核实」，**不补零、不悄悄剔除**——宁要一个诚实的缺口，不要一个好看的假数。
