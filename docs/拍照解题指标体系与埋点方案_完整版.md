# 拍照解题埋点方案（链路详解版）

更新日期：2026年9月30日。

北极星是**限时作答净增量 Δ**：相同限时、相当题目下，用产品的人均「确认采用」作答数，减去用原方式的人均采用数。埋点只为两件事：把 **M（多少人测了）、Q（做了几题）、C（采用几题）** 数准；以及回答**没采用的题卡在哪一步**。

## 一、先看链路：一道题从拍照到被采用，经过哪些站

```
开始测试 → 开始做某道题 → 拍照/上传 → 识题与精读 → 知识库检索
        → 解题 → 校验与终审 → 结果呈现 → 用户作答 → 确认采用 → 测试结束
```

每一站都可能丢用户：拍糊了（输入）、认错题（识题）、检索没依据（检索）、答错或太慢（求解）、看不懂（呈现）、不敢用（采用）。**埋点就是给每一站装计数器**——用户从哪一站流失，数据要能自己说出来，不靠猜。

## 二、每一站埋什么、为什么埋在这里

| 链路环节 | 埋点层级 | 核心事件/数据 | 为什么埋在这里 |
|---|---|---|---|
| 开始测试 | 测试窗口层 | `test_session_started`：谁、哪次测试、限时预算、产品组还是原方式组 | 计时从这一刻开始，人数 M 从这里数。预算必须由测试现场定义，服务端代记会引入时钟争议 |
| 开始做某道题 | 用户层 | `exam_attempt_started`：题目、尝试类型（首次/补拍/重试） | Q 按「开始做的题」去重：补拍、重试都还算同一道题，所以在开始时记一次，后续事件都挂在它下面 |
| 拍照/上传 | 输入层 | `exam_input_finished`：上传是否成功、补拍次数、图片质量问题 | 拍糊、反复补拍只有手机端看得见；服务端只能拿到最后一张图，看不到用户拍了三次才拍好的过程 |
| 识题与精读 | 处理层 | `exam_task_finished`（识别阶段）：识题结果、耗时、失败原因 | 认错题是后面全错的根因，只有服务端知道它把图看成了什么 |
| 知识库检索 | 处理层 | 检索是否命中、命中依据（挂在 `exam_task_finished` 的阶段数据上） | 答案的可信度一半来自「有没有依据」；检索没命中要单独暴露，不能混进「答错了」里 |
| 解题/校验 | 处理层 | 各阶段耗时、失败、重试、token 成本 | 处理耗时、成本、失败只有服务端知道——这是全链路唯一必须埋在服务端的一段 |
| 结果呈现 | 呈现层 | `exam_result_presented`：结果版本、实际显示到屏幕的时间、是否成功 | 「算完了」不等于「用户看到了」。采用只能引用用户亲眼见过的结果，所以展示回执必须由展示端出，服务端说了不算 |
| 用户作答 | 用户层 | `exam_answer_recorded`：最终作答及其版本 | 证明「形成了作答」；记下版本号，之后一旦改答，就知道旧确认要作废 |
| 确认采用 | 用户层 | `exam_adoption_changed`：采用/不采用/犹豫/撤回，绑定当前作答版本 | 北极星的 C 直接来自用户这一下点击。改了答案要重新确认，撤回不算采用 |
| 追问/查证/放弃 | 用户层 | `exam_action_recorded`：行为、起止时间 | 回答「为什么没采用」：是没看懂、不放心，还是干脆放弃了——决定下一版改哪里 |
| 测试结束 | 测试窗口层 | `test_session_ended`：退出原因、截止时每道题的最终状态快照 | 中途退出的人要留在分母里；没有这个事件，退出者的数据就凭空消失了 |

> 每条事件只带四个必带信息：**谁、哪次测试、哪道题、开始测试后第几毫秒**。其他字段服务端能补的，不让终端背。

## 三、九个事件怎么算出 Δ

- **M（人数）** ← `test_session_started`：点了「开始测试」的人都算，包括一道题没做就走的。
- **Q（题数）** ← `exam_attempt_started`：开始作答的题去重；失败、超时、放弃的题也算在内。
- **C（采用数）** ← `exam_adoption_changed`：截止时状态为「采用」的题；改过答案必须重新点一次采用，撤回的不算。
- **Δ = C产品/M产品 − C原方式/M原方式**。其余事件不进公式，负责解释「为什么」。

## 四、哪些已经埋了、哪些还没有

**已经埋了（工程层，可直接复用）：**

| 已有埋点 | 在哪里 | 记什么 |
|---|---|---|
| 模型调用计量 call_metrics | `lg_assistant/llm.py`（每次调用记录） | 每次模型调用的耗时、tokens、错误——`exam_task_finished` 的成本数据可以直接从这里拼 |
| 解题链步骤计时 progress | `lg_assistant/vision.py` 等链路各步 | capture/recognize/solve/verify 每步耗时——处理层耗时分解的现成来源 |
| 端侧判对率 routing_telemetry | `lg_assistant/nodes.py` 的 telemetry 节点 | 端侧意图 vs 云端权威路由——眼镜端链路的独立遥测，与解题九事件并行 |

**还没埋（九个事件全部）：** 应用里没有任何一处发这些事件，Web 端也没有「采用」按钮可点。建议第一批只接四个——开始测试、测试结束、开始作答、采用变化——有这四个就能算出第一版 Δ；输入、呈现、过程行为第二批再接。

## 五、防止数据打架的几条规矩（通俗版）

- **一人一期只测一轮**：产品和原方式各测一次，测第二轮的数据不收——避免「练熟了」污染对照。
- **时钟说不清就标待核实**：判断超时不靠服务器收到的时间，靠事件发生时记录的「开始后第几毫秒」。
- **同一条事件重复发只算一次**；两条同 ID 但内容不一样，整批标问题，不悄悄挑一条。
- **缺数据标「待核实」，不补零、不悄悄剔除**——宁要一个诚实的缺口，不要一个好看的假数。
